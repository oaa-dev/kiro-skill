# Knowledge Garden Setup

**Purpose:** Detect the project's tech stack, generate a stack-appropriate `docs/knowledge/schema.yaml`, and create the knowledge directory structure.

## Overview

This skill runs once per project to bootstrap the knowledge garden. It detects whether the project uses Laravel, Next.js, or both, then generates a schema with enum values tailored to that stack.

---

<critical_sequence name="setup-flow" enforce_order="strict">

## Setup Process

<step number="1" required="true">
### Step 1: Detect Stack

Run these checks in parallel to identify the project stack:

**Laravel indicators:**
```
Glob: pattern="artisan"
Glob: pattern="composer.json"
Glob: pattern="app/Models/*.php"
```

**Next.js indicators:**
```
Glob: pattern="next.config.*"
Glob: pattern="package.json"
```

If `package.json` exists, read it and check for `"next"` in dependencies or devDependencies.

**Classification:**
- **Laravel only**: `artisan` or `composer.json` exists, no Next.js dependency
- **Next.js only**: `next.config.*` exists or `package.json` has `next` dependency, no `artisan`
- **Full-stack**: both Laravel and Next.js indicators present
- **Generic**: neither detected — the knowledge garden still works, just with a stack-agnostic schema
</step>

<step number="2" required="true" depends_on="1">
### Step 2: Confirm With User

Present the detected stack and ask for confirmation:

```
Detected stack: [Laravel / Next.js / Full-stack (Laravel + Next.js) / Generic]

Is this correct?
1. Yes, proceed with [detected stack]
2. Laravel only
3. Next.js only
4. Full-stack (Laravel + Next.js)
5. Generic (stack-agnostic schema)
```

Wait for user response before proceeding.

If "Generic" was detected, still present the confirmation — the user may be on a stack the
detector doesn't recognize but still want Laravel or Next.js enums. Never force a Laravel or
Next.js schema onto a project that is neither; a forced-fit enum is worse than a generic one,
because it looks structured while being wrong.
</step>

**For full-stack projects:** Merge both schemas. Combine all enum values (deduplicate where they overlap) and include both category maps.

**Extending the schema:** These enums are a starting point, not a fixed taxonomy. When a real
problem does not fit an existing value, add a new one to `schema.yaml` (and a matching
`category_map` entry) rather than forcing the closest wrong match. A mislabeled solution is
invisible to `/kg:knowledge-insights` aggregation, which is the whole point of
having enums.
</step>

<step number="4" required="true" depends_on="3">
### Step 4: Create Directory Structure

```bash
mkdir -p docs/knowledge/solutions
mkdir -p docs/knowledge/modules
mkdir -p docs/knowledge/patterns
mkdir -p docs/knowledge/archive
mkdir -p docs/knowledge/answers
```

Create the initial critical patterns file:

```bash
# Write docs/knowledge/patterns/critical-patterns.md
```

Content:
```markdown
# Critical Patterns

Patterns promoted from solutions that must be followed to prevent recurring issues. Check this file before implementing features.

<!-- Add patterns using the /kg:compound command with "Add to Required Reading" option -->
```

Create the initial empty knowledge index at `docs/knowledge/index.md`.

**Do not write the format from memory here.** Use the empty-index template defined in the
`knowledge-index` skill ("Empty knowledge base") verbatim, replacing `YYYY-MM-DD` with the current
date. That skill owns the index format; a second copy in this file drifts from it silently.

The template must include **both** `<!-- Solutions: 0 -->` and `<!-- Modules: 0 -->`. Every command
that quick-checks the index tests for both markers before deciding whether to dispatch
`learnings-researcher` — omit either one and a freshly set-up project spawns a research agent
against an empty knowledge base on every `/kg:work`, `/kg:plan`, `/kg:review`, and
`/kg:brainstorm`.
</step>

<step number="5" required="true" depends_on="4">
### Step 5: Write Config File

Create `kg.local.md` in the project root:

```markdown
# Knowledge Garden Configuration

- **Stack**: [laravel / nextjs / fullstack / generic]
- **Rules**: [rules/laravel.md / rules/nextjs.md / both / none for generic]
- **Schema**: docs/knowledge/schema.yaml
- **Solutions**: docs/knowledge/solutions/
- **Modules**: docs/knowledge/modules/
- **Patterns**: docs/knowledge/patterns/
- **Archive**: docs/knowledge/archive/
- **Answers**: docs/knowledge/answers/
- **Setup date**: [YYYY-MM-DD]
```

Add `kg.local.md` to `.gitignore` if it exists (this is a local config file).

If a `knowledge-garden.local.md` already exists (a project set up before 0.4.0), rename it to
`kg.local.md` rather than writing a second config file.
</step>

## Error Handling

**No stack detected:**
- Offer the generic schema alongside the Laravel/Next.js options
- Proceed with the chosen stack; never guess Laravel or Next.js for a project that is neither

**Schema already exists:**
- Warn user: "docs/knowledge/schema.yaml already exists. Overwrite? (y/n)"
- If no, skip schema generation but continue with directory creation

**Directory already exists:**
- Skip creation silently (mkdir -p handles this)
